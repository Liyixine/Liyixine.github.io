记第一次全栈开发经历

一.知识预备

我在之前了解到一位学长的创业产品Mentiforce，这是一个基于AI的学习系统。此次项目起源于在Mentiforce上的一项任务，即首先利用Mentiforce上快速学习了大量知识，如何与伙伴着手开发一个LLM的应用
学习的知识主要为
操作系统
学习了进程模型、文件系统、环境变量以及网络端口等基础知识，让我能够从操作系统层面理解一条命令被执行时，进程是如何被创建、调度并参与网络通信的。
Node.js 与 V8
通过理解 V8 的 JavaScript 执行过程以及 Node.js 中事件循环和异步 IO 的机制，我明白了 Node 如何在单线程模型下高效处理大量 IO 请求，以及它在 CPU 密集型场景下的天然限制。
浏览器与请求链路
围绕一次完整的访问流程，我学习了 URL 解析、浏览器发起请求、跨域限制以及本地文件与开发服务器的区别，从而能解释浏览器与服务器之间是如何协作完成资源加载的。
浏览器渲染与 React
理解浏览器的 DOM 构建和渲染过程，并结合 React 的虚拟 DOM 和状态驱动渲染机制，我了解了页面是如何在状态变化后完成更新的。
工程化与构建工具
在项目工程化方面，我学习了 Vite 在开发和生产环境下的工作原理，包括模块加载、热更新和构建打包过程，从而理解了现代前端项目为何在不同环境下采用不同的运行策略。

在Mentiforce上面的学习让我震撼不已，学的时候并没有意识到，或者说那时候我才刚刚进入计算机的学习不久，对整个计算机的知识都不清楚，这个一整个知识链条贯穿操作系统，计算机网络，现代前后端开发

对操作系统的学习，让我了解了软件的线程进程这些概念，也知道整个操作系统在软件运行时的重要作用，如提供高级权限，上下文切换，等等；node.js的内部原理学习，让我了解了阻塞与异步，事件循环，线程池等概念，让我知道了异步，同步，并行，并发等等概念，受益匪浅；对url解析的过程的学习，让我了解了计算机网络的知识，也让我了解了客户端，服务器之间的通信过程；最后学习了react和vite等前端开发工具，拆解其原理以及为什么要这样设计的时候也让我对现代的技术栈有了更深的理解，以及开发环境，生产环境的理解

并且此次的学习基本上基于AI学习，与之前的学习大有不太，这种自上而下的学习，因为时常会出现一堆不懂的点，导致初期寸步难行，但是基于ai的功能，可以让我快速聚集各种概念，在逐渐学习许多分散的知识点后，会突然也有“顿悟”一般的感觉，正如我最开始十分不理解react vite这些软件的构建，为什么要分生产环境和开发环境，但是在学习的过程中，会突然有一瞬，就理解了这样做的理由

自上而下的这种学习方式，在人工智能的加持下变得无比强大，其学习效率和专注度确实比传统的看书上课要高上不少，这也算是一次对我学习过程的彻底颠覆

实践过程

以上是学习知识的过程，但是此时我对react和vite的理解还是处于非常浅薄的底部，react具体如何写的，后端是如何运行的，这些东西不动手实践一遍是很难理解的，于是我让AI从一个简单的列表应用开始，逐渐理解了背后的工作原理，之后再开始搭建完整的应用

CRUD记事本

为了理解react和node的原理，我先让ai做了一个简单的记事本，并且是纯前端的，在浏览完后，我已经对组件，状态，还有路由有一定理解了

之后，我告知AI我目前的基础，让其先用问卷反问我，获得我的水平之后，让其作为开发者导师教授我具体的知识，让其带领我一步步自己再搭建一遍这个简单的记事本

这一个过程让我掌握了，JSX，箭头函数，还有JavaScript的一些编程风格，HTML的基础概念，req.body, req.params, req.query等等基础概念，并且真正意义上的学习了前后端的设计哲学，比如乐观更新与后端确认后再更新的区别，REST api的设计准则，组件拆分单一职责原则，组件沟通时的设计哲学(分层的组件，context API提供全局状态，还有如redux这种第三方状态管理库)，以及前后端的设计哲学(SPA单页面应用，SSG，SSR等等，SEO需求)

这一阶段遇到的主要问题是对React，JavaScript，HTML各种不熟悉，比如我不知道react的状态不能手动更改，不然会触发状态更新，UI是状态的函数；同时也学会了组件拆分，父组件通过props传递给子组件，也了解了这种单一数据流的好处

项目初始化搭建

在完成了基本的记事本后，我真正开始应用的搭建，这一部分主要版本控制 (Git)、代码组织 (Monorepo)、模块化 (分层架构) 和环境配置 (TypeScript)

版本控制：第一次开始使用git，在这之前我对git有过了解，但是自己从未真正用过，但是实际上真的使用过后，会发现简单的使用并不复杂，仅仅只是会git add git commit就已经能够比之前写多个文件好的多，最重要的是，要先开始，如果一开始就想着自己要多么多么懂，那么我想可能我现在都不会用这个工具

代码组件与模块化：pnpm workspace 来初始化一个 Monorepo，这一块详细的让AI给我解释了前后端到底是如何交流的， Monorepo的优势，如何设计分层架构，不够当时的我显然没有考虑到部署的问题， Monorepo的架构为后续部署埋下不少隐患

环境配置：环境配置是整个过程中最折磨人的地方，这一次我打算使用的技术栈是前端React + vite，后端node + express，并且用typescript代替JavaScript，这里是最困难的，配置typescript时出现了一系列模块导入的问题，也就是CommonJS与ESM的配置矛盾，我连续进行了数次修复，最后用esModuleInterop: true解决了，这个过程非常煎熬，让我了解到环境配置的重要性，不过回头看来，这里的环境配置我实际上也没有用好一些打包好的配置工具，甚至后端的tsconfig.json还是手动创建的，这为后续部署的时候也带来了不少麻烦，但是总之这一过程让我了解到环境模板到底有多重要

认证系统：为了实现登录与注册，我了解了数据库，并且在后端使用model与数据库进行交互，了解了后端一整个流程逻辑(router -> controller -> service -> model -> 数据库)，同时为了保证安全性，我用现有的库做了一个简单的JWT验证，详细的了解了JWT token的构成和原理，这一步让我对密码加密和安全性设计原则有了进一步的了解，并且用JWT验证做了保护路由的中间组件

这一阶段，我以及对前后端的配合，已经整个数据链路条有了很清晰的了解了，同时还学会使用Postman等工具检测后端的工作，以及灵活使用前端浏览器的开发者工具来检测错误

LangChain与AI功能集成

这一阶段我亲手实现一个完整的、从非结构化文本到可检索向量的自动化数据处理流程。

首先是了解RAG的流程，询向量化、相似度检索、上下文增强和最终生成。

之后，配置langchain，接入deepseek的api，这一步看似简单，实际上处处是坑，首先AI对langchain工具链的认知还停留在过去，langchain的配置必需得找官方文档去看，这一步极大提升了我看文档，搜索解决问题的能力，之前绝大部分问题我都直接问AI获得答案的，但是这一步没办法，还有AI给出的代码基本上是基于openai的密钥，但是我需要使用deepseek的模型api，这一步需要知道安装deepseek的langchain依赖才行，之后也通过具体的langchain代码了解了，如何把prompt和需要输入的句子进行拼接，用langchain去访问大模型服务

嵌入与向量存储：这一步也处处是坑，其实我到现在都没明白pinecone和langchain还有我的嵌入模型到底是怎么工作起来的；这一步我先是注册号了pinecone，并且配合langchain和pinecone的官方文档，折腾如何将文段向量化，但是遇到的一个巨大的问题是，langchain的文档和pinecone的文档有许多不同的地方，当时我也找不到完整的示例，并且我的embedding模型是国内提供的一个qwen的embedding模型，所以我需要继承LangChain 的 EmbeddingsParams，重写一个embedding，折腾完之后，通过不断调整，最后pinecone可以正常被加入向量化的内容了，但是我最终的代码是langchain和pinecone的官方文档中的代码都不一样，是二者的拼接，解决这个问题的过程基本上就是看文档，然后拿着文档去问AI，然后自己也做一些假设，比如这个

这个的里面的config参数到底怎么配，很多都是做一些假设，比如可能并不需要PINECONE_ENVIRONMENT这个变量，然后不断尝试，最后发现自己的代码以一种奇怪的方式跑了起来，这个过程也是极其折磨人，不过好在解决了

RAG实现：解决完嵌入后，之后的工作就比较好实现了，基本上就是简单的配置好查询，并且结合langchain，用一个chain就实现了查询，到输出的结果，之后我还想实现流式输出，但是发现意外困难，无论怎么配置都有问题，就放弃了

tailwind css：之后我的应用也已经有了简单的功能了，即上传文件，提取特征嵌入，之后在对话中可以和rag的bot聊天，于是我想给整个应用做一个美化，但是我到现在为止对HTML和CSS还是一头雾水，在AI的推荐下，我打算配置tailwind css，当时这里也遇到了配置问题；目前阶段的很多AI，如果让其配置tailwind，很有可能配置的是v3的版本，会出现版本的混乱，当时配置的时候因为不知道这个问题，遇到了让我一头雾水的困难，比如去node_module中找tailwind结果压根没找到，并且typescript和tailwind也需要在一些json配置文件中配置，这些繁杂的配置文件把我弄得也是一头雾水，最后终于在官方文档的帮助下配置好了，但是我像实现比较优美的前端UI时，发现调色和搭配都十分困难，当时也不知道使用figma设计视觉

最后这个项目到了这一步就暂时停止了，虽然整体的UI非常简陋，但是还是跑通了一整个链路，收获颇丰

重拾与完善

在十一月份，随着Gemini3的出现，我也用上了Antigravity，看着丰富的AI IDE额度，我决定把之前的这个烂尾项目重拾起来，并且这也是我第一次真正意义上用AI IDE编程，以前基本上都是靠对话框中的复制粘贴完成的，这也让我了解到现在AI IDE的威力

在AI的帮助下，我依次完成了以下功能
前端UI重构：借助figma，并且模仿市面上常见的AI应用的UI，把前端的UI做了很大的调整，最后终于有一个看得过去的UI了，至少比之前毫无CSS的毛坯房或者是AI一键生成的紫色UI好了不少
长期对话存储：添加了新的model实现了对话列表
流式回复：用AI实现了之前一直没实现的流式回复功能
文件上传：实现了文件上传功能，之前只能上传文字
实现了个人资料页面：实现了个人资料页面，这个页面可以查询已经存放的rag片段，并且可以用AI生成过去的总结

到此，整个应用的功能都已经变的比较完善，UI也是勉勉强强看的过去了，但是还是有很多问题，之后又过了几天，我决定一口气把这个项目做完，最后也是连续投入了快一个星期的时间，把整个项目做成了还算不错的样子

完善

这一阶段整体的功能基本上都实现了，大部分是前端的一些重构与优化
前端的react内容重构：在大量的AI代码以及我之前写的代码上，现在的前端已经变得非常臃肿，于是我让AI进行了代码重构，自己也认真考虑了每一块UI组件的作用

整体的UI完善：之前的UI界面够看了，但是与美观来说还是相去甚远，于是我对整个chatpage,uploadpage,profilepage都进行了UI优化，还有侧边栏的优化，输入对话框的优化，并且考虑到用户使用时的一些逻辑按钮设计，还有chat页面的markdown渲染和语法高亮，这里有一个很有趣的现象，我之前实现的chat页面，无论是用户发出的内容还是AI回复的消息框都是满屏的，并且由于不是markdown的字体，导致看起来非常丑陋，我在改为markdown渲染后好了不少，但是还是缺了什么，于是我观察了其他的AI聊天应用，发现他们的消息气泡框的左右都是限制在比输入框内的，或者只比输入框超出一点点，当我把整个设计改成这样后，整体的UI美观度高了非常多

上传对话的功能：我又重新考虑了整个应用的功能，之前的使用流程是，在upload页面上传记忆，然后chat页面对话，profile页面查看已经有的记忆，并且生成总结，但是我感觉这种上传再聊天的功能实际上非常割裂，于是我便实现了一个可以直接把chat中的聊天作为记录上传的功能，或者聊天中的某段对话作为记忆上传的功能，当时的考虑是，这个功能不能像之前的upload页面，仅仅是接了一个带prompt的AI，然后生成特征，如果是这样的话，大量的聊天记录会导致生成很多特征，于是我便把这个特征提取做成了带RAG的特征提取，这样AI可以参考历史特征，以免重复输出，而单段对话的上传，我则也提供了上下的聊天内容，但是在prompt中要求AI必需以原本的对话为分析点
提示实现：为了提示用户上传对话后是否成功，又实现了一个右下角的消息提示
删除记忆的功能：考虑到删除也是一个很必要的功能，这可以让用户对自己的记忆库有更加好的掌控感，于是也实现了在profile页面删除记忆的功能

之后又是一些零零散散的UI美化，但是总体上已经趋于一个比较完善的应用了

clerk认证与部署前考量

为了将应用部署，于是我需要把之前自己手搓的JWT验证改为现代的auth验证，这个时候我已经知道实际上快速开发的时候是不建议自己手搓后端的，而是用一些SaaS服务代替，比如supabase这种服务，但是我已经做了所以没办法再做大改了，并且后端还有langchain的服务，这时候我考虑自己把前端部署到vercel上面，后端部署到render上面，这二者也都有不错的免费额度

而auth认证应该采取什么，我最开始有两个预选方案，一个是supabase，一个是clerk，最后我考虑到自己的后端没有部署在supabase上，并且clerk对用户访问控制的dashboard非常方便，便决定用clerk代替现有的认证，接着就是对后端的clerk进行一波修改了

此时出现了一个问题，如果要部署vercel和render上面，采用clerk认证，那么需要clerk用webhook发起对后盾的请求，实现数据库中新建User，但是在开发环境下，clerk不能直接请求到我的后端，同时如果真的部署到render后，由于render的免费层级的原因，render后端会休眠，那么clerk的webhook请求会失败，针对这个问题，我思考了不久，决定这么解决：首先用vercel的函数代替后端webhook的任务，这样部署环境中vercel的函数不会休眠，同时在后端实现一个懒更新，即当后端拿着已经认证的账号，但是发现数据库中没有此用户的时候再新建用户，这样可以解决本地开发时无法调试的问题，也能提供一定的保证性；而针对render之后可能的休眠问题，我决定在前端实现一个只要打开前端，就会默认去fetch一下后端的功能，实现一个”预热“，这样即便还是会等待，但是一定程度上减少了等待后端启动的时间，而在官网上装上这个，甚至可以让用户访问的时候，后端已经重新启动，并且也不违反render的条例；当时想到这个想法的时候我感到兴奋不已，这让我体验到了巧妙运用工具来解决部署中遇到实际问题。

官网搭建与产品选择

在正式部署之前，我打算搭建一个官网，同时也考虑自己第一个项目应该要叫什么名字

之前我最开始对这个项目的定位是做一个LLM克隆人，但是搭建的过程中我愈发感觉这不是很合适；考虑到我当前的功能主要是这四个

  • 上传记忆
  • 与记忆对话
  • 归档对话内容
  • 根据记忆总结
    我决定把这个应用定义为与过往进行交流，最后取名为”Then.”中文名“寻常”取自“当时只道是寻常”，“Then”这个词也有“当时”的意思，同时在编写异步中，多次写到promise.then()，也让我感觉很有程序员的味道，最后选择了这个名字

选择之后便开始官网的搭建，官网采用next.js，同时这一次我学着用已经有的现成的UI组件库，和动效库，在AI的加持下很快就实现了一个比较美观的官网，很感慨自己之前在应用中写的那些UI和效果，在现代库的加持下，只需要几行代码就能实现如此优美的特效

最后的UI美化

最后在正式部署前，我对应用和官网又不断对风格，细节，用户体验做了修改调整，比如chat页面，之前的新建页面点击就会马上创建页面，调整为了只有输入才会新建页面；实现了init页面，让新注册的账号可以通过一些问题快速启动；实现了乐观更新，不用等后端确认再渲染前端，让界面看起来不那么卡卡的；实现了应用里面的注册页面和登录页面的UI美化和跑马灯效果，还有一系列根据“Then”这个产品理念的风格，图标优化等等……

正式部署

大致实现后，就开始正式部署了，官网的部署非常轻松，大概是因为其采用了与vercel配合很好的next.js，但是应用的部署还是很曲折的，之前的单一仓库架构还有环境配置给部署带来许多隐患

首先是前端部署，

  • 一开始直接编译错误，找到原因是/api里面的webhook运行时是在node上面的，需要安装node的运行环境
  • SPA 路由 404 问题：
    • 原因：单页应用刷新时，Vercel 找不到对应的 HTML 文件。
    • 解决：在根目录添加 vercel.json，配置 rewrites 将所有请求重定向到 index.html。
  • 环境变量问题：
    • 一开始完全没考虑环境变量的问题，导致部署时，环境变量有多少都不清楚，这实际上是一开始没做好文档说明和变量名约束的，前端依赖于两个关于后端的环境变量，总之环境变量配置很混乱
      后端部署
  • Cannot find module … dist/index.js
    • 后端的配置文件中根本没写build命令，这是之前手动创建配置文件时导致的锅，而且一开始也没有在本地运行一遍，导致看render控制台报错的时候才知道
    • 另外后端配置的路径有问题，编译后的文件存储的路径找不到，并且也没有配置编译外部@shared文件的，导致各种问题，这也是之前没有解决好配置文件，以及单一仓库带来的问题
      前后端连接问题：在部署前后端都成功后，还是无法访问后端
  • CORS问题
    • 之前给后端配置跨域问题的时候，原本配置环境变量以让环境变量中的地址可以访问，但是好像这样配置不行，vercel对每个部署都会生成随机域名，当时也不知道主域名是恒定最新生产环境部署，导致没办法解决前后端的跨域问题，最后配置是让后端对所有.vercel.app结尾的域名都可以访问
  • 连接地址问题
    • 最开始给前端配置的后端环境变量直接就是地址名，没有加上/api，导致根本不能访问，定位这个问题的时候，我直接在前端的控制台fetch了一下后端，发现可以正常运行，所以不是跨域问题的锅，最后找了半天才发现原来是漏了/api，这实际上也是之前环境变量配置太乱导致的，并且注意不要加上端口号，不然也无法访问
      clerk认证问题
  • clerk库过时
    • 之前让AI做的webhook使用的是过去的clerk库，我查证之后发现这个库已经不再维护了，之后进行了调整
  • clerk发送的验证码很难收到
    • 让朋友体验的时候，发现朋友无法收到验证码，我尝试了outlook邮箱还是没办法，针对这个问题，我原本打算换为部署环境，这样的clerk发送验证码更加稳定，但是由于部署环境需要一个域名，还需要配置GitHub，Google等社交登录的Oauth，最后没有办法，我便把需要验证码认证给关闭了，但是为了风险控制，也直接关闭了外部注册的请求，不过实际上即使可以随便注册，我在最开始也实现了一个保护机制，只有clerk dashboard中账号的approved字段为true的账号才能访问后端服务，无论是前端路由还是后端路由都对其实现了保护，所以即便能注册账号也无法在未经许可的条件下访问，而实现注册保护是为了防止注册账号过多导致数据库被撑爆，但是实际上数据库即便很小，对于这种纯文本字段也是比较宽裕的
  • Webhook 验证失败
    • 前端的vercel函数会自动解析JSON，导致签名验证时 Body 不匹配，需要对解析逻辑做一些调整

最后基本上就是一些UI界面和配置的小修小改，包括手机端适配，链接跳转等等，最后基本上完成了部署

总结与未来

最后总结这一整个项目，从最开始对开发一无所知，到手搓一些复杂的逻辑，到能够用AI，官方文档，现代库快速实现一些功能，虽然这个项目还是很多不足，包括这个功能实际上也是一个简单的RAG功能，但是这整个项目对我个人能力的提升毫无疑问是巨大的，我觉得这整个过程中最有意义的几个地方是

  • React,vite,node.js,next.js,langchain,pinecone,mongoDB,tailwind等现代工具技术栈的使用
  • 整个前后端层级的设计哲学，前后端交流的设计
  • 通过阅读官方文档，解决问题的能力
  • 像考虑创业产品一样考虑UI/UX的设计
  • 灵活使用现代库和托管服务快速实现各种功能，比如supabase，clerk，还有动效库比如magicUI，使用这些现代库开发出的软件稳定性和开发速度比手写快得多
  • 生产环境/开发环境的不同与配置
  • 与强大的AI项目导向的学习，与AI IDE协作高效开发
  • 灵活应用工具链，比如vercel无服务函数实现后端的webhook，还有前端预热激活休眠的后端

但是此应用还有许多也待完善的地方

  • 缓存功能实现，因为数据库的请求很慢，无缓存导致有时候会很慢
  • 环境变量管理混乱，环境变量的命名很混乱，有些链接是硬编码的，有些又是环境变量导入的，不统一
  • 应用功能太过单调，只是一个简单的RAG应用，并且也没有在RAG上进行一些优化调整，也没有测试基准，RAG的搭建也比较简单，Embedding 模型的选择，检索策略（Top-K、相似度阈值），Chunk 策略，Prompt engineering 的迭代都有欠缺
  • UI适配，手机端还没有实现比较好的适配，以及部分的界面不美观，动效没用现代的库实现更加美观的动效

实现过程的遗憾

  • 后端很多都是自己做的，虽然可定制但是也带来了很多麻烦，最开始开发的时候没用灵活运用各种现代已经有的组件和服务，导致开发很慢，后期实现的效果也比较一般般
  • 前端到后期基本上都是靠AI完成，自己参与的优化很少，最后的前端代码框架与之前自己搭建的已经相去甚远了，到最后对HTML和CSS都没有比较坚实的基础
  • 环境配置不要想着自己手动完成，不然会造成很多麻烦
  • 最开始就考虑好比较长远的规划，不要让一开始的架构对后期的部署造成很多麻烦
  • 开发时应该写好readme文件，不然自己会忘记很多东西，导致开发受阻
  • git的提交消息写的比较烂
  • 没有实现集成测试，单元测试，只是用postman等等测试了一下
